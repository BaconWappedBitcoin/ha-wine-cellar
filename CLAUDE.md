## Key technical findings from recent work (don't re-discover these)

- **Vivino's `www.vivino.com/api/explore/explore` search API silently ignores the `q` param** for unauthenticated requests — returns the same generic "trending wines" list regardless of query (verified live, repeatedly). `search_wine()` in `vivino.py` now checks the top result for basic relevance before trusting it, falling back to HTML scraping (which *does* do real text search) when it looks wrong.
- **`api.vivino.com` (the mobile-app-facing backend) is open and unprotected** — no auth, no special headers, plain `GET https://api.vivino.com/wines/{id}` / `/vintages/{id}` / `/grapes/{id}` / `/foods` all work. Used for reliable refreshes once a wine's `vivino_id` is known (`VivinoClient.get_wine_by_id`). It has **no search endpoint** (by-id lookup only) and **no price data anywhere** — confirmed via extensive live testing (explore API, HTML scrape, real browser navigation, mobile API, even `curl` with browser-identical headers). Vivino's real price is not reliably scrapable; AI estimation (with user consent) is the fallback.
- A `Vivino Batch failed` bug turned out to be a websocket schema validation error (`ai_fallback` param sent by the frontend but not declared in the backend schema) — always check HA logs (`Paramètres > Système > Journaux`) for exact errors before guessing.
- LWIN / Liv-ex was investigated as a wine-ID/pricing source and **rejected**: the free LWIN database has no price/rating data (identification only), and Liv-ex's price data (Wine Matcher, Automation) is a professional fine-wine-trade product, not viable for this project.
- **The user reaches HA from their iPhone over `http://`, so the live camera can never work there.** Not a secure context ⇒ Safari does not expose `navigator.mediaDevices` at all ⇒ `getUserMedia` throws a `TypeError`. No code fix exists; `label-camera.ts` now detects it up front and offers the file input, which carries `capture="environment"` and opens the native camera with no secure context needed. Ruled out and not worth re-investigating: the camera components were unchanged since v1.2.5, and the two-stage front/back photo flow (v2.9.0) was **not** the cause despite the tempting timeline match.
- **Camera errors must be told apart by `err.name`, never `err.message`.** Safari's denial message is "The request is not allowed by the user agent or the platform in the current context" — it contains neither "NotAllowed" nor "Permission", so the old substring matching sent every iOS failure to the generic branch. Shared helpers live in `frontend-src/src/utils/camera.ts`.
- **Barcode scanning cannot work on iOS at all**: WebKit does not implement `BarcodeDetector`. Unrelated to the http/https question — even over https it reports "not supported on this browser". Unblocking it needs a WASM decoder (zxing); the user has never been asked about that dependency.
- **`hass.data["lovelace_resources"]` does not exist and never has** — that wrong key is why the card auto-registration silently did nothing, which is upstream issue #1 ("Custom element not found"). The collection is at `hass.data[LOVELACE_DATA]` (a `LovelaceData` dataclass, `.resources`) on current HA, or a plain `hass.data["lovelace"]` dict on older ones. Two traps around it: `async_items()` does **not** load the store (`ResourceStorageCollection` defers until a write), so an existence check reads empty and duplicates the resource on every restart — call `_async_ensure_loaded()` first; and YAML-mode dashboards have no `async_create_item` at all, so registration is impossible there by design.
- **Which add path calls what** (measured 2026-08-22, and rebalanced in #29): barcode hit ⇒ Vivino only; barcode miss ⇒ falls through to the label; label photo ⇒ AI, *plus* a non-blocking Vivino lookup fired after the details step opens; search by name ⇒ Vivino only. Before #29 the label path never touched Vivino at all, so photo-added wines had no rating and **no `vivino_id`**, which also barred them from the cheap by-id refresh. The background enrichment only ever fills gaps and never overwrites the AI's reading, the user's photo, or name/winery/vintage — and it checks the candidate really is the same wine, because Vivino answers every query with something.
- **Vivino latency, measured with the production headers**: the explore API takes 1.1–1.7 s and returns **~910 KB** for five results; grape lookups are 0.06–0.2 s each. AI label recognition is a single call, no retry, 45 s timeout — that wait is entirely the provider's (the user's is a 1min.ai relay), so there is nothing to optimise on our side beyond not lengthening it. Requests that are independent now run concurrently (`search_wine`'s explore + HTML, `lookup_barcode`'s two barcode DBs, grape names). **`fetch_extras=False` must stay sequential** — that flag exists so batch refresh does not double its request volume across the whole cellar.
- **Occupancy and placement math is shared, not re-derived**: `frontend-src/src/utils/location.ts` owns the notion of a *container* (a bin, a box, the bottom zone, or one grid slot with its depth) plus usage, labels, next-free-depth and multi-bottle planning. `utils/suggest.ts` (where a new bottle should go) and `utils/arrange.ts` (what is untidy) both build on it. It previously existed in four diverging private copies.

## Deploy workflow (Synology, no CI)

- No CI/CD, no remote dev environment. After any change: list the exact changed `.py` files + compiled frontend JS to copy, user copies them via the Synology File Station, then does a **full Home Assistant restart** (a simple integration reload is NOT enough — Python module caching).
- Frontend: TypeScript/Lit in `frontend-src/src/`, built via `npm run build` (run from `frontend-src/`) to `custom_components/wine_cellar/frontend/wine-cellar-card.js`. After any frontend change, bump `FRONTEND_VERSION` in `custom_components/wine_cellar/const.py` (format `YYYYMMDD` + incrementing letter) to bust the browser cache.
- **HACS-based testing (the user's own instance now tracks `dobunzli/ha-wine-cellar` directly via a HACS custom repository, not just Synology File Station copies)**: HACS's "update available" detection is driven by GitHub Releases, not raw commits on `main` — merging a PR to `main` alone does **not** reach the user's HACS install; only a bumped `manifest.json` `version` (semver: patch for fixes, minor for features) plus `gh release create vX.Y.Z --target main` does. **Releases are not automatic per merge (decided 2026-08-19).** After merging any PR to `main`, ask the user in chat: bump+release now, or accumulate this one with others into a single later release? Batch several merged PRs into one version bump/release when they say to accumulate — the version then reflects the cumulative changes (minor if any batched PR added a feature). Skip asking for no-op/doc-only changes (e.g. a LICENSE-only PR) — just skip the version bump for those.
- **The fork's HACS validation needed two repository *settings*, not code (fixed 2026-08-30).** GitHub creates forks with Issues disabled and no topics, and `hacs/action` fails on both — it was 7/9 checks. Issues are now enabled and the six upstream topics set (`hacs`, `home-assistant`, `home-assistant-custom-component`, `homeassistant`, `wine`, `wine-cellar`), which takes it to 9/9. Fork PR #42 also moved `actions/checkout` to v5 (v4's Node 20 is force-migrated and annotated on every run) and added `workflow_dispatch`, so validation can be re-run after a settings change without inventing a commit. Two traps. First, **`hacs/action` resolves the repository by branch name, so any run whose branch disappears under it dies** with "Not Found" → "Repository … not loaded properly in HACS". That is the missing ref, never a regression — and it bites the *original* runs, not just reruns: merging with `--delete-branch` while validation is still in flight killed both runs on PRs #42 and #43 within seconds of the merge, leaving red entries in the Actions tab while `main` itself was green. PR #44 scoped `on: push` to `main` so a PR branch no longer runs the suite twice; the surviving `pull_request` run still resolves by branch name, so **let a PR's checks finish before deleting its branch**. Second, the leftover "does not contain brands assets … falling back to the brands repository" line is informational, not a failed check.
- **After every deploy (Synology copy *or* HACS redownload) + full HA restart, also remind the user to hard-refresh the browser tab (Cmd+Shift+R).** Home Assistant's frontend is a persistent single-page app — restarting the backend does NOT reload an already-open tab's JS. Two consecutive "the fix still doesn't work" reports on this project turned out to be exactly this: the fix was correct both times, the browser tab just hadn't picked it up yet. Don't let "restart Home Assistant" alone imply the browser will pick up new code.
- Verification (no live HA access from here): `npm run build` (**now warning-free** — the 4 long-standing `TS2339` warnings came from `BarcodeLookupResult` not declaring fields the add dialog reads, and the type was completed; a new warning is a real finding, not background noise), `node --check` on the compiled JS bundle, `python3 -c "import ast; ast.parse(...)"` per changed `.py` file.
- **Local frontend preview**: `custom_components/wine_cellar/frontend/index.html` is a standalone preview page with a full mock `hass` object (mocked `callWS` for every command the card uses — wines, cabinets, buy list, history, settings, etc. — no real backend needed). `.claude/launch.json` defines `preview-server` (`python3 -m http.server 5051` in the frontend dir) which serves it directly against the last `npm run build`; `frontend-dev` (`npm run dev`, port 5050) is rollup watch only. **The preview caches hard: `location.reload()` will happily re-run the previous bundle.** Use `navigate` with `force: true` after a rebuild, and check something you just changed is actually present before concluding a fix does not work. Open it to interact with the *real* compiled component — including real mouse drag-and-drop — before asking the user to test on Synology/HACS. Includes a dedicated "Capacity Test" cabinet (a Bulk Bin already at capacity + a Spare Bin) for exercising the bin/box capacity-check logic specifically. Prefer this over writing a throwaway test harness from scratch. For a case the mock doesn't cover cleanly, a synthetic DOM `drop` event (with a hand-built `dataTransfer.getData("text/plain")` payload matching what `cabinet-grid.ts`'s real drag produces) is a reliable way to exercise `_onWineDrop` deterministically without fighting mouse-coordinate drag simulation.

## Branch / PR workflow

One branch per feature/fix, tested by the user on Synology, then PR + merge on the fork. **Branch from `main`, not from wherever you happen to be standing** — starting a second feature without checking out `main` first silently stacks it on the previous unmerged branch (happened this session; fixed with `git rebase --onto main <old-base> <branch>`, plus a bundle rebuild, since the compiled JS then contained code the branch's sources no longer had).

**Several branches open at once is a deploy problem, not just a review one**: each carries its own compiled bundle and its own `FRONTEND_VERSION`, and the user can only run one on the Synology. When they pile up, merge them and hand over a single rebuilt bundle from `main` rather than asking for several deploys. Resolve the inevitable `const.py` / bundle conflicts by **rebuilding**, never by taking one side — a bundle picked from one side no longer matches its sources. After pushing a merge commit, GitHub needs ~10–20s to recompute mergeability; `gh pr merge` fails with "not mergeable: the merge commit cannot be cleanly created" until it does. Wait and retry rather than believing it. For genuinely large sessions, group related changes into a small number of themed PRs rather than one-per-tiny-fix (discussed and agreed with the user) — but if PRs are stacked (PR B based on PR A's branch), **do not delete branch A when merging PR A** (`gh pr merge --delete-branch`) until PR B has been retargeted/merged — deleting a stacked PR's base branch auto-closes it on GitHub. Retarget or merge in the right order instead.

- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).

**Not installed everywhere.** graphify lives on the main Mac only; `~/.claude/` is per-machine and Synology Drive skips dot-folders, so nothing above travels with the repo except this file. On a machine where `graphify` is missing — or where `graphify-out/` is absent — the rules above point at a tool that is not there. Set it up first, then rebuild the graph:

```
pipx install graphifyy      # note the double y; plain "graphify" is not on PyPI
graphify claude install     # writes this section + two PreToolUse hooks
graphify update .           # ~6s, no LLM calls
```

**What it is actually good for** (measured on this repo, not assumed): `graphify god-nodes` is accurate — it named `WineCellarCard`, `Wine`, `InventoryDialog` and `WineCellarStorage` as the hubs, matching what hand exploration found. `graphify query` is much weaker: asked how photos are stored it put `photos.py` first, then listed twenty unrelated nodes and truncated at "355 more nodes cut". Treat it as a **structural index, not an answering engine** — use it to orient ("where does this mechanism live"), and read the files directly to diagnose or fix, where precision matters more than orientation.

Note the gemini large-file hook and graphify's hooks coexist deliberately: Claude Code runs every matching `PreToolUse` hook and any one of them can deny. The gemini hook is registered globally (absolute path, covers every project); graphify's are registered per-project. Do not merge them into one file — that is what caused the duplicate-firing this setup was cleaned up from.
